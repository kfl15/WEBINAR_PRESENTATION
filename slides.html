  • Which model should handle the task

Not the main focus

Main correction: we optimize our API system, not the provider's backend.
Say clearly: "OpenAI, Claude, and DeepSeek are APIs we may call. The topic is how our application reduces unnecessary calls and unnecessary tokens."
Problem

Token cost grows when a chatbot keeps sending everything.

Input grows

System prompt, chat history, documents, tools, and retrieved data enter every request.

Output grows

Long answers, explanations, and verbose JSON increase generated tokens.

Calls grow

Repeated FAQs and offline jobs can trigger unnecessary API calls.

Cost opportunity = fewer input tokens + fewer output tokens + fewer API calls

Memory is useful, but memory is not free.
Use the support bot story: "One small refund question should not require the full PDF, full chat, all tools, and a long essay."
Basics

Token cost basics

Input tokens

Everything sent to the model: instructions, user message, history, documents, tools, examples, and formatting rules.

Output tokens

Everything generated by the model. Short useful answers reduce cost and latency.

Context window

The maximum information a model can consider in one request.

API call

Every model request can cost money. Avoiding a call can be better than shrinking a prompt.

Optimization controls what goes in, what comes out, and whether the call is needed.
Transition: "Now we need a memory model for developer-built apps."
Mental Model

Put memory in the cheapest useful place.

Prompt

Only what the model needs right now.

Summary

Compressed old conversation.

Documents

Stored outside the prompt and retrieved when needed.

Answer cache

Saved answers for repeated questions.

The app decides what to remove, compress, retrieve, cache, limit, batch, or route.

The model does not know what is important unless our app chooses.
Say: "Do not put every memory directly into the prompt by default."
Technique 1

Prompt pruning: remove unnecessary prompt text.

Before

Be helpful. Be friendly. Be concise. Do not be too long. Use simple language. Give bullet points if possible.

After

Answer in simple language using 3 concise bullet points.

ManualAutomaticRisk
Remove repeated rules, unused examples, and vague wording.Trim old messages by token limit, last N messages, or relevance.Removing important context can hurt answer quality.
Names to mention: OpenAI, Claude, DeepSeek, LangChain.
Key line: "First remove noise before adding complex architecture."
Technique 2

Conversation summary: compress old chat history.

Before

Send all 40 previous messages every time the user asks a new question.

After

Send a short summary, important facts, and only the last 4-6 turns.

Summary: User wants refund for order #123. Reset email did not arrive. User prefers short step-by-step instructions.
Names to mention: LangChain, OpenAI, Claude, DeepSeek.
Warn: "Summary is compressed memory, not perfect memory. Important facts may need separate structured storage."
Technique 3

Retrieval/RAG: send relevant document chunks, not the whole library.

Store

PDF, docs, FAQ, policy files.

Search

Find chunks matching the question.

Send

Only top relevant chunks enter the prompt.

Answer

LLM writes using focused context.

RAG still uses the LLM. It saves input tokens by making the LLM read only the useful part.

Names to mention: Pinecone, Weaviate, Microsoft Azure AI Search, OpenAI vector stores.
Use the line: "RAG does not make the LLM free. It makes the LLM read only the useful part instead of the whole library."
RAG Clarification

File upload vs custom RAG

Traditional upload

A platform may handle document reading internally. Developers usually do not control chunk size, ranking, or exact context.

Custom RAG chatbot

Your app stores docs, searches them, selects chunks, and sends only relevant context to the LLM API.

Without RAG: full_document_tokens + question_tokens + answer_tokens With RAG: search_cost + relevant_chunk_tokens + question_tokens + answer_tokens
RAG saves tokens only if retrieval finds the right chunks.
This slide answers the common student confusion: the LLM still costs money, but the prompt becomes much smaller.
Technique 4

Response caching: skip the LLM when an answer already exists.

Without cache

Same FAQ question -> call LLM -> pay input tokens + output tokens every time.

With cache

Same or similar FAQ question -> return saved answer -> no LLM token cost.

Best for stable, repeatable questions: refund policy, pricing, password reset, admission rules.

Names to mention: Redis, Cloudflare AI Gateway, LangChain, vector databases.
Say: "This is application-level caching. Our app stores and returns answers when it is safe to do so."
Caching Types

Three practical cache types

Exact cache

Same question text returns the same stored answer.

FAQ cache

Approved answers for common support questions.

Semantic cache

Similar meaning returns a stored answer if similarity is high enough.

if similarity(user_question, cached_question) > 0.90: return cached_answer else: call_llm()
Warning: avoid blind caching for private, sensitive, or fast-changing answers.
Mention cache invalidation: "If the refund policy changes, cached refund answers must expire or update."
Technique 5

Output control: ask for the shortest useful answer.

Loose request

"Explain everything about password reset."

Controlled request

"Answer in 4 bullets: cause, next step, warning, contact option."

Developer controlsUse casesRisk
max_output_tokens, bullets, JSON, templates, quick/detailed modes.Support replies, classifiers, summaries, internal automation.Too-low limits can cut off important detail.
Names to mention: OpenAI, Claude, DeepSeek, support automation systems.
Key line: "The target is not the shortest answer. The target is the shortest useful answer."
Technique 6

Batch processing: move non-urgent work to the background.

Bad fit

User waits while every ticket, summary, or report is processed immediately.

Better fit

Collect, deduplicate, schedule, and process non-urgent LLM jobs later.

  • Good for ticket classification, evaluations, summaries, embeddings, reports.
  • Not good for live chat answers where the user is waiting.
Names to mention: OpenAI Batch API, Claude Message Batches, cron jobs, background queues.
Say: "Batching is useful when the work can finish later."
Technique 6

Model routing: do not use the strongest model for every task.

No model

Greeting, cached FAQ, fixed template.

Cheap model

Classification, short summary, simple rewrite.

RAG + model

Document-specific answers.

Strong model

Complex, risky, multi-step reasoning.

Route by difficulty and risk, not only by cost.

Names to mention: LiteLLM, LangChain, OpenAI, Claude, DeepSeek.
Example: "Hi" needs no LLM. A legal comparison may need a stronger model or human review.
Case Study

Support chatbot before and after

Before

  • Strong LLM for every request
  • Full policy PDF sent every time
  • Full chat history sent every time
  • Long free-form answers
  • Repeated FAQs call the LLM again

After

  • Pruned prompt
  • Summary plus recent turns
  • RAG for policy chunks
  • Cached FAQ answers
  • Short structured replies
  • Batch jobs and model routing
The user still gets support, but the app sends less memory and avoids some calls.
Walk through the sequence as a developer architecture change, not just prompt writing.

Before calling the LLM API, ask:

Can I remove it?Can I summarize it?Can I retrieve only part? Can I return cached answer?Can I limit output?Can I batch it?Can I route it?

Memory optimization is application design: keep the right information in the cheapest useful place.
